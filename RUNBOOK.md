# VPS Runbook

Everything that cannot be automated from a development machine, in order, with
the exact commands to paste. Roughly 25 minutes end to end.

Host: `103.30.146.109`, SSH port `4422`.

## Current state, measured 2026-09-13

Probed from outside the development sandbox:

| Port | Result | Meaning |
|---|---|---|
| 443 | `ECONNREFUSED` | host alive, nothing listening |
| 8000 | `ECONNREFUSED` | backend not running |
| 18789 | `ECONNREFUSED` | OpenClaw gateway not running |

`ECONNREFUSED` is a TCP reset, not a timeout: packets reach the host and it
answers. **The VPS is not suspended — it is simply running nothing.** Expect a
full bootstrap rather than a plain redeploy.

## Step 1 — Rotate the root password (do this first)

The password published in this repository's git history since 2026-09-01 is
still valid until you change it. Change it from the **IDwebhost customer panel**,
not over SSH: if someone else already has a session, an SSH password change is
visible to them.

1. Sign in at `https://my.idwebhost.com`
2. Open the VPS service, find **Reset root password** (sometimes under Manage or
   the VNC/console section)
3. Set a new password

Generate one locally rather than inventing it by hand:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(18))"
```

Then confirm the old one no longer works:

```bash
ssh -p 4422 root@103.30.146.109
```

## Step 2 — Rotate the two API credentials

Both were published in the same commit.

- **OpenClaw gateway token** — regenerate in the OpenClaw dashboard, or on the
  box with `openclaw gateway rotate-token` if your build has it. Whatever you
  choose becomes `OPENCLAW_GATEWAY_TOKEN`.
- **9router API key** — revoke the key currently in use at
  `https://9router.jcamp.io` and issue a new one. It is the value that was in
  `backend/app/core/config.py` before this change; git history still has it.

Keep both in a password manager. They never go back into the repository.

## Step 3 — Check whether the box was touched

Still worth ten seconds even though nothing is listening.

```bash
last -20                      # unexpected logins
cat ~/.ssh/authorized_keys    # keys you did not add
crontab -l                    # jobs you did not create
systemctl list-units --type=service --state=running
ls -la /tmp /var/tmp          # miners usually land here
```

Anything you do not recognise: rebuild the VPS from the panel rather than trying
to clean it. A rebuild costs 10 minutes; a missed backdoor costs the competition.

## Step 4 — Harden SSH (5 minutes, prevents a repeat)

From your own machine:

```bash
ssh-keygen -t ed25519 -C academiaclaw-deploy -f ~/.ssh/academiaclaw
ssh-copy-id -p 4422 -i ~/.ssh/academiaclaw.pub root@103.30.146.109
```

Then on the VPS:

```bash
sed -i 's/^#*PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl restart ssh
```

Keep the current session open and confirm the key works in a second terminal
before closing it.

Put the **private** key into GitHub as the `VPS_SSH_KEY` secret. The deploy
workflow is already key-only, so `VPS_PASSWORD` can be deleted from the repo
secrets.

## Step 5 — Bootstrap the application

```bash
ssh -p 4422 root@103.30.146.109

# First time on a bare box:
apt update && apt install -y git
git clone https://github.com/rofiperlungoding/academiaclaw.git /opt/academiaclaw

cd /opt/academiaclaw
git pull

OPENCLAW_GATEWAY_TOKEN='<new token from step 2>' \
NINE_ROUTER_API_KEY='<new key from step 2>' \
WHATSAPP_TO='628xxxxxxxxxx' \
./scripts/bootstrap_vps.sh
```

`WHATSAPP_TO` is your own number in E.164 without the `+`, or a group JID ending
in `@g.us`. `JWT_SECRET` is generated by the script and kept in `.env`; you never
need to supply or store it yourself.

No secret belongs in this file. That is what put a root password in the git
history in the first place.

The script refuses to run if either credential still matches a leaked value, so a
copy-paste slip cannot redeploy the compromised setup.

Expect it to stop at step 6 saying no WhatsApp channel is registered. That is the
next step.

## Step 6 — Connect WhatsApp

```bash
openclaw channels login --channel whatsapp
```

Scan the QR with the phone that should receive the briefings. Outbound sends fail
fast without an active listener, so this cannot be skipped.

Then re-run the bootstrap; it is safe to repeat and will register the automation
this time:

```bash
cd /opt/academiaclaw && ./scripts/bootstrap_vps.sh   # same env vars
```

## Step 7 — Prove the loop

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"nim":"2200000001","password":"demo1234"}' | python3 -c 'import json,sys;print(json.load(sys.stdin)["access_token"])')

# What the agent would send, without sending it
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/api/agent/briefing | python3 -m json.tool

# Force one real send now, instead of waiting for 07:00
openclaw automations run academiaclaw-briefing

# What it has actually pushed
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/api/agent/notifications | python3 -m json.tool
```

The phone should buzz on the `automations run`. That message arriving unprompted
is the shot the demo video is built around.

## If something fails

| Symptom | Check |
|---|---|
| Service will not start | `journalctl -u academiaclaw.service -n 50` |
| `JWT_SECRET is not set` | `.env` missing or unreadable; `ls -l /opt/academiaclaw/.env` should be `600` |
| Gateway shows offline | `openclaw gateway` in a screen/tmux, or `systemctl status openclaw` |
| Briefing says `nothing_due` | Correct when no deadline is within 3 days and no card is due. Add a task due tomorrow to force one. |
| Briefing says `rate_limited` | Correct. A push already went out within the hour. |
| Automation runs but no message | `openclaw automations runs academiaclaw-briefing`, then `openclaw channels list` |
| Deploy aborts on the 401 check | Intended. The API answered an anonymous request; do not expose the host until that is fixed. |

## Before recording the video

The local database ships with Indonesian seed rows from an earlier version. On
the VPS the migration adds `user_id` automatically, but old seed content stays.
To start clean:

```bash
cd /opt/academiaclaw
sqlite3 backend/data/academiaclaw.sqlite \
  "DELETE FROM flashcards; DELETE FROM academic_tasks; DELETE FROM documents;"
.venv/bin/python -c "import asyncio;from backend.app.core.seed import seed_data;asyncio.run(seed_data())"
systemctl restart academiaclaw
```
